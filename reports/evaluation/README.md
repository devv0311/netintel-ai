# `reports/evaluation/`

Generated by `npm run evaluate`. Do not edit by hand — rerun the harness.

| File | Contents |
|---|---|
| `evaluation-results.json` | Machine-readable report: run metadata, every metric with definition, numerator, denominator, ground-truth source, system input, threshold, limitations and a full breakdown, plus run-level errors. |
| `evaluation-summary.md` | Human-readable rendering of the same report: results table, pipeline stage timings, and per-metric detail including every failing case. |

Metric breakdowns, failure lists and provenance checks are all inside those two files rather than
in separate ones — `details` on each metric carries the misses (`missing`, `spurious`,
`outcomes`, `sampleFailures`), and `provenance.completeness.details.byTable` carries the
per-table provenance check.

Methodology, including what each metric counts and why two are `NOT IMPLEMENTABLE YET`:
`docs/evaluation/evaluation-methodology.md`.

## A number that is NOT supported

An earlier conversational summary used **"94% ER precision / 88% recall"** as an *illustration*
of what a good evaluation artifact might read like. It was hypothetical.

**No such figure was ever produced by code, and no such figure exists anywhere in this
repository.** A search of `docs/`, `src/` and `README.md` for `94%`, `0.94` and any precision or
recall claim returns nothing but the `TO BE DEFINED BEFORE IMPLEMENTATION` placeholders in
`docs/evaluation/evaluation-spec.md`. Treat that number as unsupported and do not quote it.

The measured entity-resolution numbers are in `evaluation-results.json`, and they must be read
together with `er.mentionCoverage` — the pairwise scores are computed only over mentions the
pipeline actually produced, and it does not produce all of them.

## Scope of every number here

One corpus (Operation DarkNet Delhi), one seed (20260901), one commit. Nothing in this directory
demonstrates generalisation to any other data. See
`docs/evaluation/real-world-generalisation-test.md`.
