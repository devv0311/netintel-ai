# Real-World Generalisation Test — Design (NOT EXECUTED)

**Date:** 2026-09-03 · **Status:** design only. **No data has been collected. The research gate remains closed.**
**Blocked on:** the Option B decision (`docs/architecture/public-data-schema-options.md`) and the fix to `er.mentionCoverage`
**Depends on:** `docs/data-research/public-data-adapter-design.md`

---

## 1. The question

> **Does the existing entity-resolution architecture work on real-world entity variation?**

Not "how accurate is it" — *whether the architecture holds at all*. The current resolver
(`src/lib/resolution/resolve.ts`) has exactly two merge rules:

- **Tier A** — two mentions merge when their own evidence item states the same phone, account or
  vehicle identifier.
- **Tier B** — a mention with no identifier of its own merges into a Tier-A cluster when its
  **exact name string** matches exactly one such cluster.

On Operation DarkNet Delhi that yields pairwise precision and recall of 100% (`reports/evaluation/`).
It has to, on reflection: the corpus was generated by the same codebase, so every alias appears
in the casing and script the resolver compares. The experiment exists to find out what those
numbers become when the strings are not ours.

**Stated prediction, recorded before the run so it cannot be adjusted afterwards:**
Tier A will hold up well — an LEI is an identifier and identifier matching is sound. **Tier B
will fail badly on real data.** Exact-name matching cannot survive corporate suffix variation,
transliteration, or name ordering, and there is no third tier to catch what it misses. If that
prediction is wrong, that is a genuinely good result and worth knowing.

## 2. Scope — deliberately small

| | Wikidata | GLEIF |
|---|---|---|
| Subjects | ≤ 2,000 | ≤ 5,000 |
| Query | 3 bounded SPARQL queries, explicit `LIMIT` | one Golden Copy file, filtered to `IN` jurisdiction |
| Size | < 50 MB | < 100 MB |
| Licence | CC0 | CC0 |
| PII | public figures only, minimal fields (adapter §3.3) | legal entities only |

Under 150 MB total. This is not a collection pilot; it is one experiment with one question.

### Wikidata queries (bounded, illustrative — to be reviewed before any run)

1. **Indian companies with an LEI** — `?item wdt:P31/wdt:P279* wd:Q4830453 ; wdt:P17 wd:Q668 ; wdt:P1278 ?lei`
   → the cross-source linkage set; every row is a gold GLEIF↔Wikidata pair.
2. **Indian organisations with Hindi and English labels** — both `rdfs:label` languages required
   → the transliteration set.
3. **Subsidiary relations among (1)** — `wdt:P749` / `wdt:P355`
   → the relationship-recall set.

Every query carries an explicit `LIMIT`, a descriptive `User-Agent` with a contact address, and
429 backoff. No crawl, no unbounded query, no dereferencing of anything beyond the endpoint.

## 3. What is being tested, case by case

Each row is a hypothesis with an expected failure mode. The point is to see which fire.

| # | Variation | Concrete example | Current mechanism | Expected outcome |
|---|---|---|---|---|
| 1 | **Identifier matching** | Two records sharing LEI `335800…` | Tier A | **Holds.** Baseline: if this fails, something is wrong with the adapter, not the resolver |
| 2 | **Corporate suffixes** | `Reliance Industries Limited` vs `Reliance Industries Ltd.` vs `RELIANCE INDUSTRIES LTD` | Tier B exact match | **Fails.** Three clusters where one is correct |
| 3 | **Transliteration** | `भारतीय स्टेट बैंक` vs `State Bank of India` | Tier B exact match | **Fails.** No transliteration awareness anywhere in the codebase |
| 4 | **Name ordering** | `Narayana Murthy, N. R.` vs `N. R. Narayana Murthy` | Tier B exact match | **Fails** |
| 5 | **Abbreviation / initialism** | `TCS` vs `Tata Consultancy Services` | `aliases[]` may carry it | **Partial** — succeeds only where the publisher recorded the alias |
| 6 | **Unicode normalisation** | NFC vs NFD Devanagari; ZWJ/ZWNJ; combining marks | adapter applies NFC; resolver does none | **Watch.** If the adapter's NFC is doing the work, that is a resolver gap the corpus hid |
| 7 | **Case and whitespace** | `PVT LTD` vs `Pvt Ltd`; double spaces | Tier B is byte-exact | **Fails.** The cheapest fix available, and the one to try first |
| 8 | **False-positive risk** | Two distinct `Kumar Enterprises Pvt Ltd` with different LEIs | Tier B merges on exact name | **The dangerous case.** A wrong merge is worse than a missed one — it asserts two companies are one |
| 9 | **Ambiguous match** | A name matching several Tier-A clusters | flagged `ambiguous`, never merged | **Holds by design** — and nothing ever revisits it, so measure how large the ambiguous pile gets |
| 10 | **Cross-source linkage** | Wikidata QID ↔ GLEIF LEI via `P1278` | Tier A, if the LEI is extracted as an identifier | **Should hold** — the sharpest single test of Tier A |

## 4. Metrics

The harness already computes all of these; only a corpus filter and a publisher-identifier
ground-truth adapter are needed (`public-data-adapter-design.md` §6).

| Metric | Reference | What a bad number means |
|---|---|---|
| `er.pairwise.precision` | shared LEI / QID | over-merging distinct real companies — **the serious failure** |
| `er.pairwise.recall` | shared LEI / QID | Tier B missing variants — the expected failure |
| `er.cluster.exactMatch` | identifier clusters | how often a real entity is recovered whole |
| `er.alias.attachment` | publisher `aliases[]` | alias handling on strings we did not write |
| `rel.recall` | GLEIF L2 parent/child | relationship extraction on real ownership edges |
| **ambiguous rate** *(new)* | — | share of decisions left `ambiguous` — the size of the pile nothing revisits |
| **per-variation breakdown** *(new)* | rows 2–8 above | which failure mode dominates, so the fix is targeted |

The last two are new and small; both are per-decision counts over `resolution_decisions`.

## 5. Protocol

1. **Freeze the resolver.** Record the commit. `src/lib/resolution/resolve.ts` is not touched for
   the duration of the experiment. Any change is a finding to be applied afterwards and re-measured.
2. **Ingest as a separate investigation.** The public corpus must never share an investigation
   with Operation DarkNet Delhi — the demo is labelled synthetic-only
   (`dossiers.synthetic_data_only`) and mixing real entities into it would make that label false.
3. **Run the pipeline unmodified** through corroboration.
4. **Score**, partitioned by corpus, and publish both corpora's numbers side by side.
5. **Classify every error** into the rows of §3 by hand, on a sample of at least 50. The
   aggregate number is far less useful than knowing which of rows 2–8 produced it.
6. **Record the prediction outcome.** State plainly whether §1's prediction held.

## 6. Stop conditions

Halt and report rather than pressing on if:

- any collected record contains personal data beyond the adapter's allowed fields;
- the licence or terms of either source differ from what `source-registry.csv` records;
- a rate limit or access restriction is encountered;
- provenance cannot be populated for any record;
- ingestion needs a change to any existing evidence type.

## 7. What this experiment does *not* answer

- Nothing about documents. Both sources are structured; the free-text extraction path does not
  exist. SEC filings and court judgments remain untested and unaddressed.
- Nothing about Indian *personal*-name resolution at scale. Wikidata's Indian people are public
  figures with clean labels — easier than the real case, not harder.
- Nothing about the Copilot, contradiction detection, or spatial/temporal corroboration; the
  public corpus has no ground truth for any of them.
- Nothing about performance at scale. 7,000 subjects is a correctness experiment, not a load test.

## 8. Cost and honest expected value

Two SPARQL queries, one bulk file, under 150 MB, a day of engineering once `public_record` exists.

The expected value is not a good score. It is a **specific, evidenced list of which name
variations break Tier B** — turning "exact name matching probably won't survive real data" from
an opinion into a table with counts. That is worth more before a demo than after one.
