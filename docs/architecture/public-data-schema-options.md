# Public-Data Schema Options (Decision Required)

**Date:** 2026-09-03 · **Status:** decision pending — **no schema change has been made**
**Inputs:** `docs/architecture/current-system-assessment.md`, `docs/data-research/source-registry.md`, `reports/evaluation/evaluation-summary.md`

---

## The problem in one paragraph

`EVIDENCE_ITEM_TYPES` (`src/lib/domain/evidence.ts:38`) is a closed twelve-value enum, and seven
of those values name data categories the project's own governance rules prohibit collecting —
FIRs, CDRs, phone records, bank-account records, suspect records, IMEI records, witness
statements. No legitimately obtainable public source publishes anything in those shapes. So
"use real public data" fails at the Zod enum before licensing, PII or provenance is even reached.
There are exactly two coherent responses.

---

## Option A — Keep the closed schema

The pipeline continues to accept only the twelve investigative record types. Public data never
enters. The Phase 1 source registry becomes a compliance artifact showing the sourcing question
was assessed properly and answered *no*.

**Advantages**

- Zero engineering cost, zero risk to a working seven-stage pipeline and 466 passing tests.
- Zero new privacy surface. Nothing that could carry real personal data is ever ingested.
- The demo path stays deterministic and rehearsable; `docs/demo/demo-contract.md` is unaffected.
- The evaluation numbers just produced stay meaningful, because the distribution does not move.
- Honest framing available: the system is a demonstrator for *authorised* investigative data, and
  the schema is deliberately shaped like the data an authorised deployment would receive.

**Disadvantages**

- Nothing is ever tested against real-world entity variation. The 100% entity-resolution scores
  in `reports/evaluation/` describe a corpus whose name strings were generated by the same
  codebase that resolves them.
- "Real-world OSINT" cannot be claimed in any form.
- The gap stays invisible until someone external asks the obvious question.

**Migration cost:** none. **Privacy:** best available. **Effect on demo:** none.
**Effect on evaluation:** none. **Effect on future ML:** neutral — there is no ML to affect.

---

## Option B — One additional evidence type: `public_record`

Add exactly one type. Not four, not a family.

```
EVIDENCE_ITEM_TYPES = [ …the existing twelve…, "public_record" ]
```

with a content shape that is a **discriminated envelope**, not a new taxonomy:

```ts
public_record.content = {
  recordRef: string;            // "gleif:5493001KJTIIGC8Y1R12", "wikidata:Q42"
  registry: string;             // "gleif" | "wikidata" | …  (data, not a Zod enum)
  registryRecordId: string;     // the identifier as the publisher issues it
  subjectKind: "person" | "organisation" | "place";
  name: string;                 // the publisher's primary name
  aliases?: string[];           // other names/labels the publisher records
  identifiers?: { scheme: string; value: string }[];   // LEI, ISIN, Wikidata QID, …
  relations?: { predicate: string; targetRegistryRecordId: string }[];
  location?: { label: string; latitude?: number; longitude?: number };
  observedAt?: string;          // publisher's own as-of date
  retrievedAt: string;          // when we fetched it
  license: string;              // "CC0-1.0"
  licenseUrl: string;
  sourceUrl: string;
}
```

**Why one type and not four.** `registry_record`, `filing` and `document_record` would each need
their own extractor, their own tests, their own graph mapping and their own place in the
evidence-classification rules — four times the surface for the same information. `registry` as a
free-text field inside one type gives the same expressiveness with one extractor. If a genuinely
different *structure* appears later (a long-form filing needing free-text extraction), that earns
its own type then, on evidence, rather than now, on speculation.

**Can public records be expressed through this without weakening the investigative schema?**

| Concern | Answer |
|---|---|
| Source metadata | Yes — `registry`, `sourceUrl`, `license`, `licenseUrl`, `retrievedAt` are richer than any existing type carries, and are the fields the source registry demands. |
| Document metadata | Partly. Registry records are structured, not documents. A real *document* source (SEC filing, judgment) would need free-text extraction, which does not exist. That is why the adapter starts with GLEIF and Wikidata and not with SEC. |
| Structured fields | Yes — `identifiers[]` is a superset of what `phone_record`/`bank_account_record` express. |
| Entities | Yes — `subjectKind` maps onto `ENTITY_KINDS`; `organisation` needs a **new entity kind** (see cost below). |
| Relationships | Yes — `relations[]` maps to `relationship_mention`, the same shape `phone_subscriber` already uses. |
| Events | Weakly. Registry records are states, not events. Acceptable: the pilot targets entity resolution, not event extraction. |
| Evidence spans | Yes — provenance location becomes `${recordRef}#${fieldPath}`, exactly as today. Nothing in the provenance model changes. |

**Advantages**

- Real name variation, real transliteration, real corporate suffixes reach the existing resolver,
  which is the only way to learn whether Tier-B exact-name matching survives contact with reality.
- Additive: the twelve existing types, their extractors and their tests are untouched.
- Provenance model, classification taxonomy and evaluation harness all carry over unchanged.
- CC0 sources only, so no licence obligation propagates anywhere.

**Disadvantages and honest costs**

- `ENTITY_KINDS` (`src/lib/domain/entity.ts:16`) has no `organisation`. Adding one touches entity
  persistence, graph node typing, the analytics graph and probably the UI legend. This is the
  single largest cost in Option B and it is not small.
- A second corpus means the store holds two provenance universes. Evaluation must be partitioned
  by corpus or the DarkNet Delhi numbers become uninterpretable.
- Wikidata records living people. Even at CC0, an investigative graph over named living people is
  a different artifact from a public knowledge base, and the PII screening described in the
  source registry becomes load-bearing rather than theoretical.
- Real risk of scope creep: `public_record` invites "just one more registry" indefinitely.

**Migration cost, measured against the current tree**

| Change | Files | Size |
|---|---|---|
| Add enum value + content schema | `src/lib/domain/evidence.ts`, `src/lib/corpus/manifest-schema.ts` | small |
| Add extractor | `src/lib/extraction/extract.ts` (one function + one `EXTRACTORS` entry) | ~80 lines |
| Add `organisation` entity kind | `src/lib/domain/entity.ts` + resolution/graph/analytics/UI touchpoints | **medium — the real cost** |
| Graph mapping for `relations[]` | `src/lib/graph/build.ts` | ~60 lines |
| Adapter + fixtures | new `src/lib/adapters/public/` | new module |
| Tests | extraction, resolution, graph, adapter | ~200 lines |
| DB migration | one Drizzle migration; no column changes needed | small |

No existing column changes. No existing row rewrites. That is the strongest argument for
Option B: it is genuinely additive.

**Effect on the synthetic demo:** none, provided the public corpus is ingested as a *separate
investigation*. If both land in one investigation the graph mixes fabricated and real entities,
which is unacceptable for a demo that is labelled synthetic-only (`dossiers.synthetic_data_only`).

**Effect on evaluation:** the harness needs a corpus filter. Ground truth for the public corpus
is thin by nature — GLEIF LEIs and Wikidata QIDs are gold *identifiers*, so entity-resolution
ground truth comes free, but there are no expected communities, contradictions or Copilot answers.
Expect a small, sharp metric set, not a mirror of the DarkNet Delhi one.

**Effect on future ML:** neutral today. There is no model. If a supervised component is ever
added, `public_record` is where its training pairs would come from — but that is a consequence,
not a justification.

## Recommendation

**Option B, scoped hard, and only after the decision in §5 of the recommendation report is
answered — but not yet built.**

Reasoning, in order:

1. The evaluation just produced makes the case. `er.pairwise.precision` and `recall` are 100% and
   `er.alias.attachment` is 18/18 — on a corpus where every alias was written by the generator in
   the same casing the resolver compares. Those numbers cannot distinguish "the resolver is good"
   from "the corpus is easy". Only real name variation can, and Option A guarantees it never
   arrives.
2. `er.mentionCoverage` is 84.8%, and the misses are all three money mules, who never become
   person entities at all. That is a live defect in the current pipeline on the *easy* corpus.
   **Fix that before adding a harder one.**
3. Option B is additive and reversible. Nothing in the twelve existing types changes.
4. The `organisation` entity kind is the honest cost centre. Anyone estimating Option B as
   "add an enum value" is underestimating it by an order of magnitude.

**Sequencing, non-negotiable:**

1. Fix the M1/M2/M3 extraction gap, re-run the evaluator, confirm coverage reaches 100%.
2. Set thresholds for the metrics that now have numbers (`evaluation-spec.md` §3 requires this
   before a feature is marked Demo Ready).
3. *Then* implement `public_record` behind the adapter design in
   `docs/data-research/public-data-adapter-design.md`.
4. Run the generalisation experiment in `docs/evaluation/real-world-generalisation-test.md`.

**What would change this recommendation:** if the answer to "will NetIntel AI ever handle real
data?" is a firm no — a demonstrator for authorised deployment only — Option A is correct and
this document should be closed as decided.
